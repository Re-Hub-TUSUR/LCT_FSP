# KADRY — backend

FastAPI + SQLAlchemy 2 (async) + PostgreSQL. Архитектура и правила слоёв — в [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md).

## Требования

- Python 3.12 (`.python-version`)
- [uv](https://docs.astral.sh/uv/) 0.8+
- PostgreSQL 17 (локально или `docker compose up db`)

## Запуск

```bash
cp ../.env.example ../.env   # один .env на весь репозиторий; заполните JWT_SECRET
uv sync                      # зависимости + dev-группа
uv run alembic upgrade head  # миграции
uv run python -m app.seed    # демо-данные (необязательно)
uv run uvicorn app.main:app --reload
```

Swagger: <http://localhost:8000/api/docs>, OpenAPI: `/api/openapi.json`.

Сгенерировать секрет: `uv run python -c "import secrets; print(secrets.token_urlsafe(48))"`.

## Банк заданий

Стартовый банк платформы лежит в `app/seed/data/assessment/`: 600 вопросов (`quiz.json`, `quiz/*.json`),
57 задач на код (`code.json`, `code/*.json`) и по шаблону теста на грейд (`tests.json`).

Задание привязано к грейду сложностью, а не напрямую: шаблон грейда берёт заданное число заданий
каждого уровня.

| Грейд  | Мин | Вопросы специализации | Общие вопросы | Задача на код |
| ------ | --- | --------------------- | ------------- | ------------- |
| Intern | 25  | 6 лёгких              | 4 лёгких      | лёгкая        |
| Junior | 30  | 4 лёгких + 4 средних  | 2 лёгких + 2 средних | лёгкая |
| Middle | 35  | 6 средних + 2 сложных | 4 средних     | средняя       |
| Senior | 40  | 3 средних + 5 сложных | 2 средних + 2 сложных | сложная |
| Lead   | 40  | 2 средних + 4 сложных | 3 по архитектуре, 3 по управлению, 2 сложных | сложная |

Уровни: лёгкий вопрос — узнать одно базовое понятие, средний — применить его в типовой ситуации,
сложный — взвесить компромисс, найти причину отказа, знать внутреннее устройство. Лёгкая задача
решается одним проходом по данным, средняя требует стандартного приёма (хеш, стек, сортировка с
жадным шагом, обход в ширину, скользящее окно), сложная — динамического программирования,
взвешенного графа или поиска по ответу.

Задания авторские: за основу взяты классические сюжеты, условия и все тесты написаны заново.

**Добавить вопрос** — строка в `quiz/<специализация>.json` или `quiz/general.json`:
`[специализация | null, тема, "e" | "m" | "h", вопрос, верный ответ, три неверных]`. Вопрос — до
200 символов; неверные варианты должны быть сопоставимы по длине с верным.

**Добавить задачу на код** — объект `CodeTask` в `app/seed/code_bank/{easy,medium,hard}.py`: условие,
эталонное решение, открытый пример и генератор закрытых тестов. Ожидаемые ответы вручную не
пишутся: сборщик запускает эталон, а для средних и сложных задач сначала сверяет его с наивным
решением на случайных малых входах.

Тесты проверяют, что у каждой специализации на каждое правило шаблона есть двойной запас вопросов
и не меньше пяти задач на код, что эталоны проходят собственные тесты и что JSON собран из
актуальных исходников. Идентификатор задания выводится из текста вопроса или ключа задачи, поэтому
правка формулировки добавит новую строку в уже развёрнутую базу, а старую не изменит — её нужно
выключить в админке.

## Демо-данные

Все компании и люди вымышленные; почты — на зарезервированном домене `example.com`.

| Файл | Что внутри |
| ---- | ---------- |
| `app/seed/data/companies.json` | 20 компаний из разных отраслей и городов, у каждой аккаунт работодателя |
| `app/seed/data/vacancies.json` | 97 вакансий (3 черновика): все специализации словаря и все грейды, вилка зарплаты обязательна |
| `app/seed/data/candidates.json` | 124 соискателя: все 10 специализаций, грейды от стажёра до лида, 38 треков стека (Go-бэкенд, Unity, SOC…) |

Граничные случаи, на которых стоит проверять ленты и поиск: соискатели без истории ФСП (ТЗ:
обязательный случай), с привязанным FSP ID, но без результатов, без пройденного теста
(`assessmentScore = null`: грейд заявлен самим кандидатом), скрытые от работодателей
(`is_visible_to_employers = false`), вакансии-черновики (`published_at = null`).

**Аккаунты.** Пароль у всех демо-аккаунтов один: `kadry-demo-2026` (на публичном стенде задайте
свой через `SEED_USER_PASSWORD`).

- `candidate@example.com` — соискатель: Middle Python-разработчик из Москвы с результатами ФСП;
- `employer@example.com` — работодатель, компания «ПэйФлоу»;
- `employer2@example.com` — работодатель, компания «Северный код»;
- остальные работодатели — `recruiter@<key>.example.com`, соискатели — поле `email` в
  `candidates.json`.

**Как устроено.**

- JSON собирает детерминированный генератор (`generate.py`, фиксированный seed) из курируемого
  контента (`content.py`): треки специальностей со стеком и формулировками, города, вузы,
  компании и планы вакансий. Правьте `content.py` и пересобирайте JSON; тест сверяет файлы с
  генератором.
- Даты хранятся как «дней назад» и отсчитываются от момента загрузки, поэтому демо не устаревает.
- Id записей — UUIDv5 от ключа фикстуры: повторная загрузка удаляет прежние демо-записи
  (вместе с приглашениями к ним) и создаёт их с теми же id, ссылки не ломаются.
- Поле `track` (например, `go-backend`) в БД не пишется: это эталонная разметка для оценки
  качества подбора — пары «вакансия — кандидат» одного трека и соседнего грейда релевантны.
- С `APP_ENV=production` загрузка требует флага `--force`; если демо-почта уже занята чужим
  аккаунтом, загрузка останавливается без изменений.


## Статус доменов

Реализованы:
- health, users/me, categories/dictionary, admin/users;
- auth: регистрация, подтверждение почты, вход, refresh-токен в cookie с ротацией, выход;
- кабинет: `/candidates/me` (резюме, дополнительные резюме, фото, привязка FSP ID, распознавание
  файла резюме — ниже) и `/companies/me`;
- ленты подбора и поиск кандидатов (ниже);
- календарь встреч (`/calendar/events`);
- тестирование: категории, шаблоны, попытки, запуск кода, тестовые задания, банк задач и тестов
  компании;
- чат (`/conversations`): сообщения, вложения, приглашения на встречу;
- уведомления (`GET /notifications/stream`, SSE) и отклики (`/responses`).

Заглушки с финальным контрактом (пути, схемы, роли), отвечают `501 not_implemented`: публикация
и правка вакансий (`POST /vacancies`, `PATCH /vacancies/{id}`), анкета тестирования
(`POST /assessments/survey`), приглашения
(`/invitations`), заявки (`/applications`), подбор под потребность (`/matching`).

Уведомления живут в памяти процесса, поэтому API должен работать одним процессом uvicorn (так его
и запускает compose). Вложения чата лежат в `UPLOAD_DIR` (по умолчанию `/data/uploads`); в Docker
это том `upload-data`, а каталог в образе принадлежит пользователю `app`, от которого работает API.

## Распознавание резюме

`POST /candidates/me/resume` (multipart-поле `file`: PDF или DOCX до 5 МБ) возвращает черновик полей
анкеты. Ни файл, ни черновик не сохраняются: соискатель проверяет поля и сохраняет форму как обычно.

1. Текст извлекается на сервере (`app/services/resume_text.py`): PDF — через `pypdf` (до 10 страниц),
   DOCX — стандартной библиотекой. Скан без текстового слоя и PDF с паролем отклоняются с понятной
   ошибкой.
2. Почта, телефон и Telegram заменяются на `[скрыто]` до отправки модели; телефон и Telegram попадают
   в черновик прямо из файла.
3. Текст (до 20 000 символов) уходит в [RouterAI](https://routerai.ru) (`app/services/resume_reader.py`)
   со строгой JSON-схемой ответа: специализация — из словаря, формат работы — `office/hybrid/remote`.
4. Ответ модели проверяется (`app/services/resume_import.py`): неизвестная специализация, чужие
   форматы, дубли и слишком длинные навыки, нереальные стаж и зарплата отбрасываются.

Модель задаёт `RESUME_PARSER_MODEL`, по умолчанию `openai/gpt-6-luna`: строгая JSON-схема, 11 ₽ за
миллион входных и 56 ₽ за миллион выходных токенов (каталог RouterAI, октябрь 2026), то есть около
10 копеек за резюме. Без `ROUTERAI_API_KEY` эндпоинт отвечает 503, и форма предлагает заполнить поля
вручную. Стоимость каждого запроса пишется в лог API.

Текст резюме без контактов, но с именем и опытом, обрабатывает провайдер модели: у
`openai/gpt-6-luna` это серверы в США. Если данные должны оставаться в России, в каталоге есть
`yandex/aliceai-llm-flash` (провайдер Yandex, около 70 копеек за резюме); строгую JSON-схему эта
модель не заявляет, поэтому с ней нужен пустой `RESUME_PARSER_REASONING` и проверка на реальных
резюме.

## Ленты подбора

Все списки постраничные: `?page=1&perPage=20` (до 100), ответ —
`{items, total, page, perPage, pages}`.

| Метод | Кто | Что |
| ----- | --- | --- |
| `GET /vacancies/feed` | соискатель | только релевантные вакансии (специализации всех резюме и смежные, свой и соседние грейды), по убыванию соответствия, с причинами; фильтры `workFormat`, `salaryMin`; `view=all\|unseen\|liked\|matched\|skipped` |
| `PUT/DELETE /vacancies/{id}/reaction` | соискатель | `{"kind": "like"\|"skip"}`: избранное / «не показывать» |
| `GET /vacancies/reactions/counts`, `GET /candidates/reactions/counts` | соискатель / работодатель | сколько карточек в списках `liked`, `matched`, `skipped` |
| `GET /candidates` | работодатель | поиск по банку: `q`, `specialization`, `grade[]`, `stack[]` (все), `hasFspAchievements`, `verifiedOnly`, `workFormat[]`, `city` (+ готовые к переезду), `salaryMax`, `experienceMin`, `vacancyId`, `view`, `sort=relevance\|assessment\|salary\|experience` |
| `PUT/DELETE /candidates/{id}/reaction` | работодатель | избранное / пропуск (+ `vacancyId`, под какую вакансию) |
| `GET /candidates/{id}` | соискатель (свой), работодатель | профиль; контакты — себе и работодателю, чьё приглашение принято |
| `GET /vacancies`, `GET /vacancies/{id}`, `GET /companies/{id}` | все | публичный список (без черновиков), карточки |
| `GET /vacancies/mine` | работодатель | вакансии своей компании, черновики первыми |

`view=unseen` скрывает всё, по чему уже принято решение, — так работает колода свайпов;
`view=all` скрывает только пропущенные. Списки своих решений (в интерфейсе «Отобрано / Взаимно /
Вырезано»): `liked` — избранное, `matched` — взаимный интерес (рекрутер лайкнул кандидата, а
кандидат — любую вакансию этой компании; флаг `matched` есть и на карточке), `skipped` —
пропущенные, их можно вернуть.

**Ранжирование** (`app/services/matching.py`) — одна объяснимая модель для обеих сторон, 100
баллов: специализация 20 (второе резюме в этой профессии — 15, смежная — 10), грейд 20 (соседний —
10), стек 25 × доля технологий
вакансии, формат работы 10, город 5 (удалёнка — всегда, переезд — 3), зарплата 10 (ожидания в
вилке; до +10% — 5), бонус 10: у соискателя — свежесть вакансии, у рекрутера — сила профиля.
Сила профиля (0–1) = 0,6 × балл теста + до 0,4 за результаты ФСП: внутри категории первыми
идут подтверждённые профили (ТЗ 2.1). Без вакансии рекрутер видит порядок по силе профиля.
Каждая карточка несёт причины своей позиции.

**Поиск** (`app/search/`): Elasticsearch с русской морфологией, синонимами ИТ-сленга («питон»,
«сеньор», «кубер»…) и опечатками. Формулу соответствия считает Painless-скрипт с той же
арифметикой, что и Python, поэтому Elasticsearch и резервный поиск по базе (когда
`ELASTICSEARCH_URL` пуст или кластер недоступен) возвращают одинаковый порядок; поле `engine`
показывает, кто ответил. Любое изменение `fit()` повторяйте в скрипте (`app/search/query.py`) и
проверяйте тестом на живом кластере (ниже): CI его пропускает. Индекс — версия за алиасом:
пересборка не прерывает поиск. В `_meta` индекса хранится отпечаток его описания
(`INDEX_VERSION`): если код поменял поля или анализаторы, API пересоберёт индекс сам при первом
поиске. Перед поиском индекс догоняет профили, изменённые с прошлой синхронизации (`updated_at`):
так кандидат, только что сдавший тест, сразу виден работодателю.

| Команда | Что делает |
| ------- | ---------- |
| `uv run python -m app.search` | пересобрать индекс из базы (сид делает это сам) |
| `TEST_ELASTICSEARCH_URL=http://localhost:9200 uv run pytest tests/test_search_elastic.py` | сверить выдачу Elasticsearch и базы на демо-данных |
