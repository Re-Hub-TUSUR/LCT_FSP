# Правила, чтобы не ломать CI

CI (`.github/workflows/ci.yml`) запускается на каждый pull request и на каждый пуш в `main`.
Красный `main` ломает работу всем, кто подтянет изменения, и прячет новые ошибки: CI показывает
только первую.

## Что проверяет CI

| Job | Что делает | Где |
| --- | --- | --- |
| frontend | `npm ci`, `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm test`, `npx vite build` | `frontend/` |
| backend | `uv sync --frozen`, `ruff check .`, `ruff format --check .`, `mypy`, `pytest` | `backend/` |
| migrations | `alembic upgrade head`, `alembic check`, `alembic downgrade base` на PostgreSQL 17 | `backend/` |
| docker | сборка образов `backend` и `frontend`, `docker compose config` | корень |

Job останавливается на первом упавшем шаге. Если упал `ruff`, то `mypy` и тесты в этом прогоне
не запускались. Сборка Docker-образов ждёт зелёных frontend и backend и до тех пор пропускается.
Поэтому один красный CI может прятать сразу несколько ошибок, а образы — неделями не собираться.

## Перед каждым пушем

```bash
# frontend
cd frontend && npm run format:check && npm run lint && npm test && npm run build
# backend
cd backend && uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
```

- `npm run build` уже включает `typecheck`.
- Хук pre-commit (husky + lint-staged) проверяет только изменённые frontend-файлы. Для бэкенда
  хука нет: ruff и mypy запускайте сами.
- Автопочинка: `uv run ruff check --fix . && uv run ruff format .` и `npx prettier --write .`.
  Перед коммитом посмотрите diff.
- Менялись модели или миграции: `uv run alembic heads` должен показать одну голову, а на поднятой
  базе (`docker compose up -d db`) — `uv run alembic upgrade head && uv run alembic check`.
- Менялись Dockerfile, зависимости или `docker-compose.yml`: `docker compose build`.

## Правила для людей

1. **Не пушьте в `main` с красными проверками.** Лучше через pull request: CI проверит ветку до
   слияния, и `main` останется зелёным.
2. **Красный `main` — общий стоп.** Сначала чиним его, новые фичи поверх не пушим. Чинит тот, кто
   сломал, или пишет в чат, что не успевает.
3. **Поменяли интерфейс — обновите тесты в том же коммите.** Если тест упал после вашего
   изменения, сначала разберитесь, что сломано: тест или поведение. Пример: тест свайпов упал,
   потому что после редизайна перестали работать стрелки ← →, — это был баг, а не устаревший тест.
4. **Миграции:** одна голова, у каждой рабочий `downgrade`, модели совпадают со схемой
   (`alembic check`). Перед новой миграцией подтяните `main`: две миграции от одного родителя дают
   две головы.
5. **Зависимости** добавляйте только через `uv add` и `npm install <пакет>` и коммитьте вместе с
   `uv.lock` и `package-lock.json`: CI ставит пакеты строго по lock-файлам.
6. **Секреты не коммитим.** `.env` в `.gitignore`, ключи хранятся в `.env` и в секретах
   репозитория. Тесты не ходят во внешние платные сервисы.
7. **Демо-данные** в `backend/app/seed/data` собирает генератор
   (`uv run python -m app.seed.generate`). Если поправить JSON руками, упадёт тест сверки.
8. **После пуша** откройте Actions или выполните `gh run list --branch main` и убедитесь, что
   прогон зелёный.

## Правила для ИИ-агентов

Для Claude Code, Cursor, Codex и любых других агентов, которые меняют этот репозиторий.

1. **Перед словом «готово» прогоните все проверки** из раздела «Перед каждым пушем», каждую
   отдельно, а не цепочкой до первой ошибки, и приведите результат. Не утверждайте, что CI
   зелёный, пока не проверили `gh run list` и `gh run view`.
2. **Сначала посмотрите CI на `main`** (`gh run list --branch main --limit 3`), потом ищите
   виноватого: падение может быть старым и чужим.
3. **Не покупайте зелёный CI ценой проверок.** Не удаляйте и не ослабляйте тесты, не добавляйте
   `.skip`/`xfail`. Не ставьте `# noqa`, `# type: ignore` и `oxlint-disable` без причины в
   комментарии. Если поведение изменили намеренно — обновите тест и напишите почему. Если тест
   поймал баг — чините код.
4. **Python запускайте через `uv run --frozen …`**, чтобы случайно не переписать `uv.lock`; новые
   зависимости ставьте через `uv add`. На фронтенде, если зависимости не меняются, — `npm ci`, а не
   `npm install`.
5. **Не трогайте инварианты без их проверок:**
   - формула `fit()` в `backend/app/services/matching.py` и Painless-скрипт в
     `backend/app/search/query.py` меняются только вместе; проверка —
     `TEST_ELASTICSEARCH_URL=http://localhost:9200 uv run pytest tests/test_search_elastic.py`
     (в CI она пропускается);
   - миграции — одна голова и чистый `alembic check`;
   - демо-данные — только через генератор.
6. **Тесты фронтенда:**
   - при старте приложение всегда делает `POST /auth/refresh` и `GET /candidates/me` (или
     `/companies/me`), поэтому заглушки `fetch` сопоставляйте по пути, а не считайте все вызовы;
   - в jsdom нет вёрстки: если интерфейс зависит от размеров (переполнение, `scrollHeight`),
     подменяйте их через `vi.spyOn` и восстанавливайте после теста;
   - первая отрисовка ленивой страницы может идти дольше секунды: `findBy…(…, { timeout: 5000 })`.
7. **Тесты бэкенда работают без сети.** Внешние сервисы (RouterAI, onlinecompiler, Resend,
   Elasticsearch) подменяются через `app.dependency_overrides`, а ключи в тестах пустые.
8. **Переводы строк — только LF** (`.editorconfig`, `.gitattributes`). На Windows скрипт легко
   записывает CRLF.
9. **Коммиты и пуши — только по явной просьбе человека.** `--no-verify` не используйте.

## Если CI красный

1. `gh run list --branch main --limit 5` покажет, с какого коммита началось.
2. `gh run view <id> --log-failed` покажет первую ошибку. Следующие шаги в этом прогоне не
   запускались.
3. Прогоните все проверки локально, каждую отдельно: так виден полный список.
4. Почините одним коммитом и в сообщении напишите, что сломалось и почему.
